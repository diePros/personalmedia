# v1.4 OAuth for MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Model policy: **sonnet** implements, **opus** reviews, **fable** only for management or critical reviews. This milestone touches authentication and key handling, so the milestone review is a **critical review (fable)**.

**Goal:** claude.ai custom connectors and Hermes (`auth: oauth`) connect to PMS's MCP endpoint through OAuth 2.1 (DCR + PKCE). The user consents and chooses the scope in the browser. Grants are listed and revocable in Settings.

**Architecture:**
- PMS is both the authorization server and the resource server on one origin.
- OAuth access and refresh tokens reuse the existing token-wrap mechanism (`secret_kek` → wrap UMK). They are just new token *kinds* with an expiry and a grant id.
- `tokens::authenticate` accepts them alongside `pm_` tokens.
- Grant metadata sits in the encrypted index DB (as `TokenMeta` with an optional `grant` field in its JSON, so the index schema doesn't change).
- `system.db` migration v3 adds kind, expiry and grant id to the token rows, plus an `oauth_clients` table.

**Spec:** `docs/superpowers/specs/2026-11-16-personal-media-design.md` §13b (binding), plus §5, §9, §13, §14.

## Global Constraints

### Database and wire format
- **Ruling P:** `system.db` goes to v3 through a numbered migration with a migration test from a real v2 DB. The index DB schema is unchanged. Extend `TokenMeta.scope_json` using `#[serde(default)]` fields.
- **Token formats:**
  - Access token: `pma_{32 hex id}_{64 hex secret}`
  - Refresh token: `pmr_{32 hex id}_{64 hex secret}`
  - Static tokens stay `pm_…`.
  - AAD: `pm/v1/umk/token/{id}`, the same as static tokens. The kind is in the row; the id namespace is shared.
- **Lifetimes:**
  - Access token 3600 s
  - Refresh token 30 days, single-use and rotated
  - Authorization code 60 s, single-use, held in memory only. It maps to the pre-minted pair and stores `client_id`, `redirect_uri`, the S256 challenge and `scope`.

### OAuth endpoints (all under `PM_PUBLIC_URL`)
- `GET /.well-known/oauth-protected-resource` (also served at `/.well-known/oauth-protected-resource/mcp`)
- `GET /.well-known/oauth-authorization-server`
- `POST /oauth/register`
- `GET|POST /oauth/authorize`
- `POST /oauth/token`
- `POST /oauth/revoke`
- Metadata and JSON responses use `Cache-Control: no-store`.

### Scopes and consent
- **Scope strings:** `mcp:read`, `mcp:write`, `content:full`, `offline_access`. Requested scopes only pre-select the consent form; **the consent form is authoritative**. The granted scope string is echoed in the token response.
- **Consent page text (exact):** `{client_name} wants access to your documents`. The callback line reads `It will send you back to: {redirect host}` in bold. The client name is HTML-escaped and truncated to 64 chars.
- Consent choices map to `TokenScope { access, content, tags }`, using the same allow-list semantics as static tokens, including "Restrict to a new tag".

### Redirect URIs, revocation and errors
- **Redirect allow-list:** exactly as spec §13b. Comparison is exact string match for the claude hosts. For loopback, any port, with the host `127.0.0.1` or `localhost`, scheme `http`, and the path as registered.
- **Revoking:** a grant's revoke in Settings deletes all its token rows plus its meta, and evicts the token cache.
- **Error codes** follow RFC 6749 §5.2: `invalid_request`, `invalid_client`, `invalid_grant`, `unauthorized_client`, `unsupported_grant_type`, `invalid_scope`. Never put secrets in error descriptions.

### Logging, CSRF and limits
- **Logging:** client ids and grant ids are fine. Never log tokens, codes, code_verifier or state.
- **CSRF:**
  - The token, register and revoke endpoints are cross-origin by nature (claude.ai's servers and the Hermes CLI). Exempt exactly those three from the origin guard and CSRF, and document it in code.
  - The authorize POST (consent) stays session + CSRF protected.
- **Limits:**
  - DCR: 10 per IP per hour, at most 200 clients. Prune clients with no grant after 24 h.
  - Token endpoint failures count toward the existing `mcp-ip:` limiter, under Ruling O semantics.

### Gate
- Every task ends with `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` (with `PM_TEST_MODELS_DIR=$HOME/.cache/pms-test-models`). **The controller re-runs the full suite before merge.**

## Review Focus
1. An authorization code can't be used twice, after 60 s, with a different `client_id` or `redirect_uri`, or with a wrong `code_verifier` (`auth_code_single_use_and_bound`).
2. A refresh token works exactly once. Replaying an old one fails with `invalid_grant` and revokes the whole grant (reuse detection) (`refresh_reuse_revokes_grant`).
3. An expired access token returns 401 with the `WWW-Authenticate` header, so clients refresh (`expired_access_token_401_with_metadata_pointer`).
4. A grant revoked in Settings stops working immediately, even with a cached access token (`revoke_grant_kills_access_and_refresh`).
5. Registering a non-allowed redirect URI fails, and so does using an unregistered one at authorize (`redirect_uri_allow_list_enforced`).
6. A consent with `metadata_only` + tag restriction yields tokens that enforce exactly that through the existing MCP scope tests (`oauth_scope_enforced_like_static_tokens`).

### Task 27: Authorize, consent, token, refresh, revoke

**Files:** `src/oauth/{authorize,token}.rs`, `src/tokens.rs` (mint pair; `authenticate` handles `pma_` with expiry; refresh rotation; grant revoke), `templates/oauth_consent.html`, `src/user_db/meta.rs` (`#[serde(default)] grant: Option<GrantInfo { client_id, client_name, redirect_host }>`).

**Behaviour:**
- `GET /oauth/authorize` validates `response_type=code`, `client_id`, `redirect_uri` (registered and allowed), `code_challenge` + `code_challenge_method=S256`, and `state`. It also accepts the `resource` parameter; if present it must equal `{PM_PUBLIC_URL}/mcp`.
  - Not logged in → login, then back to authorize. Reuse the continue-cookie pattern with `__Host-pm_continue`.
  - Any validation error before the redirect URI is trusted renders an error page and **never redirects**.
- `POST /oauth/authorize` (consent):
  - approve → mint the pair (two wrap rows + grant meta), create the code, then redirect to `redirect_uri?code=…&state=…`
  - deny → `error=access_denied`
- `POST /oauth/token`:
  - `grant_type=authorization_code`: verify the code, client, redirect URI and PKCE, then return `{access_token, token_type:"Bearer", expires_in:3600, refresh_token, scope}`.
  - `grant_type=refresh_token`: unlock with the refresh secret, mint a new pair, delete the old rows, keep the same grant. Reuse of a consumed refresh token deletes the entire grant.
- `POST /oauth/revoke` deletes the token, and the grant if it's a refresh token. Always 200.

**Tests** (`tests/oauth_flow.rs`): the full happy path driving HTTP like a client (register → authorize with a logged-in session → consent → code → token → MCP `tools/list` with the access token → refresh → old refresh fails), plus Review Focus items 1–6.

Commit: `feat(oauth): authorization code + PKCE, consent, rotating refresh tokens`.
